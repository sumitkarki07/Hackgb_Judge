# Security

## Authentication and authorization

Judge codes contain 128 bits of unpredictable material, formatted as eight groups of four hexadecimal characters. The format is deliberately longer than the example brief. Apps Script has no documented CSPRNG suitable for credentials, so the deployment secret is generated by Node's `crypto.randomBytes(32)`. Token material is derived through HMAC-SHA-256 over a persistent monotonic counter, time and a UUID, with that 256-bit private key. The counter increments under the application lock. Security depends on the secret, not on UUID unpredictability. Codes and sessions use distinct HMAC contexts.

Only code verifiers are stored in Judges. Code issuance returns the plaintext once; no retrieval endpoint exists. Rotation changes the verifier and credential version, instantly invalidating old codes and sessions. Judge sessions last 12 hours and organizer sessions 2 hours; only verifiers are stored in Sessions. Logout removes the current session. Judge status and code version are checked on every request; organizer allowlist membership is checked on every request.

Only event name, date and venue are returned by the unauthenticated branding endpoint. All other application data requires a session.

The judge token is stored in localStorage to survive a new tab opened by a QR scan. Organizer sessions use sessionStorage. Neither is put in a URL. This choice supports mobile QR workflows within HTML Service, which does not expose ordinary application-set HttpOnly cookie handling. Treat the browser as trusted only for holding a bearer token, never for role, judge ID, assignment ID or claimed identity. Sign out on shared devices. Server rendering escapes user content; external URLs require HTTPS; no user HTML is inserted into trusted markup.

Every protected RPC operation authenticates the session and gates the role before the operation handler executes. Judge project and evaluation operations resolve the authenticated judge's active assignment server-side. Client-provided judge IDs are ignored as identity. Judges receive only their assignments and own current evaluations; private team member fields, judge lists, other evaluations and result standings are withheld.

## Organizer Google OAuth

The web app runs as its owner. `Session.getActiveUser().getEmail()` is not an authentication source. There is no admin password, browser email assertion, public bootstrap endpoint or production demo login.

The authorization-code flow uses a five-minute single-use state, independent private polling proof, nonce and S256 PKCE. A popup visits Google. The callback validates the pending state and exchanges the code at the fixed `https://oauth2.googleapis.com/token` endpoint with the client secret over certificate-validated HTTPS, with redirects disabled. Access/ID tokens are not sent to the browser or persisted. The browser never supplies an ID token to a decoding function.

**Token authenticity:** this uses Google's documented server-flow trust model: a token obtained directly from Google's token endpoint over authenticated, intermediary-free HTTPS is trusted as Google-issued. The app still verifies issuer, exact audience, authorized party, expiry, issued time, nonce, nonempty subject and `email_verified === true`. It does not use the debugging `tokeninfo` endpoint or decode an untrusted browser JWT. If this architecture changes to accept tokens from a browser or another component, add full JWKS signature verification before accepting them.

The allowlist is a private JSON array in Script Properties. The Google `sub` is the session's stable subject; verified lowercased email is checked for authorization. Only the originating tab's polling proof can collect the approved identity and create a session. OAuth authorization codes and state appear in Google's standard callback URL; **judge codes and application session tokens never do**. Callback HTML sets a no-referrer policy, loads no external resources, and contains no identity/token details. Users should close the popup after returning to the original tab.

See [Google's OpenID Connect server flow, step 5](https://developers.google.com/identity/openid-connect/openid-connect#obtainuserinfo) and [token validation trust boundary](https://developers.google.com/identity/openid-connect/openid-connect#validatinganidtoken). Live compatibility with the actual OAuth client, deployment and Workspace policy must be verified before use.

## Abuse controls

Apps Script HTML Service does not provide a trustworthy client IP for per-IP rate limiting. The implementation uses a persistent global judge-login ceiling (120/minute), bounded code-verifier buckets (8/15 minutes), Google-start ceiling (30/minute), and Google-poll ceiling (120/minute). Failed requests consume their budgets. Judge rate buckets are bounded to 256 Script Properties to prevent unbounded random-key property exhaustion; occasional bucket collisions can require a judge to wait. Session/flow expiration and pruning bound stored authentication records during normal use.

These controls limit brute-force work and quota use but cannot prevent public endpoint denial-of-service. Do not describe them as a WAF or abuse-proof infrastructure. Use the live load rehearsal to verify headroom for the event account. A login rate error is explicit; it never silently drops an evaluation.

## Data protection

- Workbook general access must be Restricted; public and domain link sharing are rejected on every repository access.
- Organizers' account allowlist does not automatically grant spreadsheet editor permissions. Share the workbook and script only with trusted maintainers.
- All inputs are validated server-side with lengths, enum values, numeric ranges, allowed fields and HTTPS URL checks. CSV uses a parser with quoting support and an explicit comma delimiter; duplicate headers/IDs and malformed rows are rejected.
- Sheets writes use `userEnteredValue.stringValue` with typed JSON encoding. User text cannot become an executable spreadsheet formula. CSV exports prefix formula/control-leading cells with an apostrophe.
- Assignment changes and corrections preserve historical records. The API has no generic delete operation or destructive migration endpoint.
- Significant admin mutations, submissions, rankings and corrections are audited. Audit details never contain plaintext codes, session tokens, client secrets or Google tokens.
- Backups use restricted Drive copies in the owner's Drive root. Their sharing is verified. Backup contents include protected credential verifiers and must remain private.
- Spreadsheet snapshots and audit data are private organizer exports, never published assets.
- `exceptionLogging` is disabled in the Apps Script manifest and RPC errors do not expose stack traces or provider response bodies. Code does not log credentials. Closing a code dialog removes its plaintext from the DOM.
- Production transport is Google HTTPS. Local HTTP is exclusively the isolated development fixture.

## Finalization and recovery

Confirmed awards cannot be edited. Once any award is confirmed, underlying project/judge metadata and evaluation reopening are locked, and judging cannot be reopened. Finalized and Archived events reject ordinary business mutations. Authentication/session housekeeping and authorized backups can still operate; backup creation adds an audit entry.

No destructive migrations are shipped. A future destructive change requires a fresh private backup, a reviewed migration, and explicit owner confirmation. Restoring also requires a fresh backup of the current state and deliberate confirmation, described in DEPLOYMENT.md. Rotate `AUTH_SECRET` after restore or suspected compromise to invalidate restored codes and sessions; regenerate judge codes as needed.

## Dependency and operational review

The runtime bundles Papa Parse, qrcode and jsPDF locally; there is no remotely loaded executable JavaScript. Font loading from Google Fonts is optional and does not receive application records. Lockfile and CI make builds repeatable. Run `npm audit` and review advisories before the event. A passing test suite is not a penetration test or live deployment certification.
